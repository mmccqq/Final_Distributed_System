Evaluating a Microservices Architecture for Scalable Multi-Agent AI Systems

Planner→Researcher+Analyst→Writer

Francis · Luochun Xiao · Xinyue Xuan · Xuetao Li

Say: We want to find out when splitting a multi-agent AI app into microservices pays off, and when it only adds network cost.

Expanded 02 · Problem

Agents in one app have very different resource needs

  • Multi-agent AI apps chain agents and tools that differ in cost: one waits on an LLM, one is I/O-bound on search, one burns CPU running code.
  • A monolith scales them together, so you pay for idle parts to relieve one bottleneck.
  • Splitting into microservices allows independent scaling, but adds network hops, coordination, and new partial-failure modes.

Evidence the trade-off is real

Fan-out systems are ruled by their slowest call (Dean & Barroso, The Tail at Scale, CACM 2013). Microservice graphs move bottlenecks into RPC and networking (Gan et al., DeathStarBench, ASPLOS 2019). Prime Video moved one pipeline from microservices back to a monolith and cut its cost by 90% (Prime Video Tech blog, 2023).

Stakeholders

  • Teams building agent products (support copilots, research assistants) need latency that stays flat as users grow.
  • Platform and SRE engineers must choose a deployment shape and want evidence for when to split.
  • Cost owners pay for compute and LLM calls; scaling everything to fix one agent wastes money.
  • End users should not see the whole answer hang because one tool is slow.

Popular frameworks such as AutoGen, LangGraph and CrewAI run agents in one process by default; how to distribute them is left to the deployer.

Say: Name the stakeholder first. "If you run an agent product, you have to decide how to deploy it, and nobody gives you numbers." Then cite the Prime Video case to show splitting is not always right.

Added 03 · What we build

A research-assistant pipeline with a realistic task mix

A user submits a question. The Planner splits it into steps, the Researcher and Analyst run in parallel, and the Writer merges the result.

Task typeSharePath
Quick answer60%Planner → Writer
Research30%+ Researcher → Web search, Vector store
Analysis10%+ Analyst → Code sandbox (CPU-heavy)

The mix is a starting point and a variable we can change: shifting it moves the bottleneck from one service to another.

Why a mock LLM

Real LLM APIs are costly, rate-limited and noisy, which would swamp our measurements. A mock LLM service returns canned text after a delay drawn from a configurable distribution, and can inject errors.

This keeps runs repeatable and lets us study the architecture, not the model provider. One small run against a real API checks that the mock is realistic.

Say: The point of the mix is heterogeneity. If every task looked the same there would be nothing to scale independently.

Expanded 05 · Research questions

Two questions, each with a testable hypothesis

RQ1 · Scalability

How does microservice decomposition affect throughput and tail latency as workload increases?

H1. At low load the monolith has lower latency, because it makes no internal network hops. As load grows, the decomposed system sustains more throughput before saturating, because it can scale the busiest service alone.

H2. Scaling only the bottleneck service reaches the same throughput as scaling the whole monolith with fewer vCPUs.

RQ2 · Resilience

How well do microservices and failure-isolation mechanisms keep the system working when parts fail?

H3. In the monolith, a slow or crashed agent ties up shared threads and slows every task type. In the decomposed system with timeouts, circuit breakers and bulkheads, only tasks that need the failed service are affected.

We would count either outcome as a result. If the monolith wins, we report the load level where the crossover would happen.

Say: Hypotheses make the experiments falsifiable. Say clearly that the monolith could win.

Expanded 09 · Observation

Measure at four levels, from the client to a single request

Client

Locust

Offered load, throughput, p50/p95/p99, error counts. This is what users feel.

Service

Prometheus + Grafana

Per service: request rate, errors, latency. Also queue depth, in-flight requests per bulkhead, circuit-breaker state.

Infrastructure

CloudWatch

CPU and memory per ECS task, running task count, ALB target response time.

Request

Traces and server logs

A trace ID follows each task through every hop, so we can split latency into network vs. compute time.

Server logs record lock wait time on the monolith's shared in-process state, to show where its contention comes from.

All four views use the same timestamps and run IDs, so a latency spike in Locust can be traced to the service and the hop that caused it.

Say: The lock-contention logs matter for the monolith: if it saturates, we want to show whether the cause is locks or CPU.

Added 10 · Why this is a distributed system

Independent processes that share nothing but messages

PropertyWhere it shows up in our system
Separate machinesEach agent and tool runs as ECS tasks; replicas land on different hosts.
Message passing onlyOrchestrator, agents and tools talk over HTTP/JSON. No shared memory.
Partial failureOne service can crash while others keep running; callers only learn about it through timeouts.
No global clockEvents across services are ordered with trace IDs and logical timestamps, not wall clocks.
Concurrency on shared stateMany tasks run at once; task state in Redis must stay correct when steps are retried.
Scale-out and load balancingAn ALB spreads requests; each service autoscales on its own.

Say: The monolith is our control. It runs the same logic without these properties, which is how we isolate their cost.
